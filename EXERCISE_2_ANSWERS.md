  is ES modules; `type: "module"` is also what lets `vite.config.js` and `eslint.config.js` use plain

- `.gitignore`: `node_modules/`, `dist/`, plus editor/OS noise and `.env*`.
- First real dependency: `vite` (devDependency). `package-lock.json` was generated by `npm install`
  and is meant to be committed alongside `package.json` (see Q3).

### Questions

**What problem does a package manager actually solve that "download the library and put it in a
folder yourself" doesn't? Be specific.**

Three concrete things, none of which "download it yourself" gives you: (1) **transitive dependency
resolution** — Vite itself depends on dozens of packages (rolldown, lightningcss, picomatch, ...),
each with their own version constraints; `npm install` resolves a consistent graph across all of
them, which is infeasible to do by hand once the graph is more than 2-3 packages deep. (2) **version
constraints and updates** — `package.json` records *ranges* (`^8.3.0`), so `npm install` (or `npm
update`) can pull in compatible patch/minor fixes later without you re-downloading and re-wiring
anything by hand. (3) **a reproducible, shareable manifest** — `package.json` + `package-lock.json`
together are enough for anyone (or CI) to reconstruct the *exact* `node_modules` this project needs,
which "I copied a folder into my project" can never guarantee once two people's copies drift.

**What's the difference between `dependencies` and `devDependencies`? Which category will Vite, your
linter/formatter, and TypeScript belong to, and why?**

`dependencies` are packages the *shipped application* needs at runtime (e.g., a UI framework your
bundled code actually imports and calls). `devDependencies` are packages only needed to *develop or
build* the project — they never end up inside the code a browser executes. Vite, ESLint, Prettier,
and TypeScript are all `devDependencies` here: none of them are imported by `js/*.ts` at runtime, all
of them are tools that run before/around the code (bundling, linting, formatting, type-checking).
This project in fact has zero runtime `dependencies` at all — the app itself still has no third-party
runtime library, exactly as before the migration; only the tooling changed.

**What is a lockfile for, and what could go wrong for your teammates (or CI) if it weren't committed?**

`package.json`'s version ranges (`^8.3.0`) are intentionally loose. `package-lock.json` pins the
*exact* resolved version (and the exact version of every transitive dependency) that `npm install`
actually picked, the moment it was generated. Without it committed, two teammates running
`npm install` a week apart — or a CI run six months from now — could each resolve a *different* set
of versions that all technically satisfy the ranges in `package.json`, but behave differently: a
minor version bump in a linter can add new rules that suddenly fail CI; a bundler patch release can
change chunk-splitting behavior. "Works on my machine" becomes literally true and unfalsifiable
without a lockfile, since there's no longer one canonical set of versions to compare against.

**If you chose pnpm: ... If you chose npm: what would you gain or lose by switching to pnpm on a
larger project?**

Chose npm (see below for why); on a larger project, moving to pnpm would trade: **gain** — pnpm
stores every package version once in a global content-addressable store and *hard-links* it into
each project's `node_modules`, so N projects sharing a dependency use disk space roughly once instead
of N times, and installs are correspondingly faster once the store is warm; pnpm's `node_modules`
layout is also strict by default (a package can only `require()` what it actually declares as a
dependency, not whatever happens to be hoisted to the top level), which surfaces "phantom dependency"
bugs npm's flatter hoisting can hide until a version bump reshuffles the tree. **Lose** — one more
tool contributors need installed (`corepack enable` or a separate pnpm install) instead of npm, which
already ships with Node; occasional friction with packages that assume npm/yarn's looser hoisting and
break under pnpm's strictness until a `.npmrc` shamefully-hoist exception is added.

Why npm for *this* project specifically: it ships with Node (zero extra setup for anyone in the
course), and an 11-module single-app project has no multi-package workspace or meaningfully large
`node_modules` for pnpm's disk-sharing to pay off on.

### Questions

**What's the difference between a plain static file server and Vite's dev server? Name one thing
Vite's dev server does that a plain static server doesn't.**

A plain static server (`python -m http.server`, `npx serve`) does exactly one thing: given a request
path, read that exact file off disk and send its bytes back unchanged. Vite's dev server instead sits
in front of a **transform pipeline**: every request for a `.ts` file is compiled to plain JS
on the fly (type-stripped, no separate build step needed — confirmed directly: `curl`ing
`/js/utils.js` returns valid runtime JS with every type annotation gone, even though the file on disk
is `utils.ts`); it rewrites bare import specifiers to real URLs; it injects the `@vite/client` HMR
script into `index.html`; and it can serve TypeScript, JSX, or any other Vite-plugin-supported syntax
without a separate compile pass. None of that is possible from a server that only serves bytes
verbatim.

**What is Hot Module Replacement, and what specifically did you observe happen (and *not* happen,
e.g. to app state) when you triggered it?**

HMR is the dev server pushing an updated module to an already-running page over a WebSocket
connection and having the page's module runtime re-evaluate just that module (and anything that
statically can't avoid re-running) *in place* — no navigation, no full document reload — provided
something in the update chain actually accepts the update (`import.meta.hot.accept()`).

Tested this precisely, live, in a real browser, with a canary: before each edit, set
`window.__hmrCanary = <unique value>` via the console — an arbitrary in-memory global with no
connection to the app's own code, which only a *full page navigation* can destroy (a true in-place
module swap leaves the rest of the page's JS realm, and therefore this variable, completely alone).

- **Editing `js/dashboard.ts`** (app code): the page's content visibly updated within about a
  second, with no visible flash/navigation — but the canary was gone afterward (`window.__hmrCanary`
  → `undefined`). So this *looked* like HMR but was actually a **full page reload**: Vite's
  WebSocket client walked the import graph from `dashboard.ts` up to `main.ts`, found nothing along
  that chain calling `import.meta.hot.accept()` (this app never does — it's plain vanilla TS with no
  HMR-awareness written into it), and fell back to its documented default for an unacceptable
  update: reload the whole page. State that *looks* preserved (the bookmark count, the reviewed
  count) is actually just `localStorage` re-read from scratch on the fresh load, not survived
  in-memory state — a hard reload would show exactly the same thing.
- **Editing `styles.css`**, same canary test: the header color changed instantly, and the canary
  **survived** (`window.__hmrCanary2` still held its original value afterward). CSS is a case Vite
  hot-swaps by construction — it patches/replaces the injected `<style>` tag in place — without
  needing any `accept()` call from application code at all, unlike JS/TS module updates.

So the honest answer to "what did and didn't happen to app state": for **this specific app**, editing
application TypeScript never actually exercises true HMR at all — every visible "hot update" during
this session's dev work was a full reload the whole time, just a fast one. Editing CSS is the one
case where real, in-place HMR happens. To get true JS-level HMR here, the code itself would need to
opt in (e.g. `if (import.meta.hot) import.meta.hot.accept();` in an entry module) and actually handle
re-applying state on update — nothing in this codebase does that, since it predates this migration
and was never written with HMR in mind.

**Why does an app already split into ES modules integrate naturally with a tool like Vite, compared
to the original single-`<script>` version?**

Vite's entire dev-server model is built around the ES module graph: it needs `import`/`export`
statements to know what depends on what, so it can transform and serve exactly the modules a page
actually requests (and only re-transform the ones that changed, for HMR) instead of treating the app
as one opaque blob. A single `<script>` file has no import graph at all from Vite's point of view —
there'd be nothing to split into separately-transformable, separately-cacheable units, and no HMR
boundary to invalidate to just one function's worth of code. The Exercise 1 module split (11 files,
each `import`ing exactly what it uses) is precisely the shape Vite is designed to consume; this
migration needed zero module-boundary changes to work with Vite, only a folder move for static
assets.

## Demo 3 — Production build & preview

### Tasks — what was done

`npm run build` (`tsc --noEmit && vite build`) produces `dist/`:

| File | Size | Note |
|---|---|---|
| `index.html` | 10.78 kB | references hashed bundle via relative `./assets/...` paths |
| `assets/index-ZAWMSz9M.css` | 11.44 kB | every `styles.css` rule, minified into one file |
| `assets/index-*.js` | 22.65 kB | all 12 `js/*.ts` modules, bundled + minified + type-stripped |
| `data/*.json`, `assets/logo/*`, `assets/people/*` | unchanged | copied through from `public/` verbatim, unhashed |

`vite preview` was run against this build (not the dev server) and every route re-checked with
`curl`: `/`, the hashed JS bundle, the hashed CSS bundle, and `data/case.json` all returned `200`,
confirming the app works end-to-end from the actual built artifact rather than from source.

### Questions

**Name at least three concrete transformations Vite applied to your source when building for
production.**

1. **Bundling** — 12 separate `js/*.ts` module files became one `assets/index-*.js` file; the browser
   makes one request for app code instead of 12 (plus whatever each imports transitively).
2. **Minification** — comments and type annotations stripped, whitespace removed, local variable
   names shortened (`evidenceList` → `e`, etc., observed directly in the built output), and even
   small stylistic normalizations like switching string-literal quoting to backticks where shorter.
   The combined original `js/*.ts` source is ~59 KB; the minified bundle is ~23 KB.
3. **Content-hashed filenames** — `index-ZAWMSz9M.css`, `index-ByDM04Ed.js`: the hash is derived from
   the file's own content, so a future deploy that changes the JS produces a *different* filename
   (see the next question).
4. (bonus, also directly observed) **Static asset passthrough** — `public/data/*.json` and
   `public/assets/*` are copied into `dist/` completely unprocessed, unlike the JS/CSS which get
   transformed — Vite only bundles/minifies what's actually part of the module graph or referenced
   from processed CSS/HTML.

**Why do production filenames typically include a content hash? What problem does that solve?**

Browsers and CDNs aggressively cache static assets by URL, often for as long as a year, to avoid
re-downloading unchanged files on every visit. If `app.js` kept the same filename across deploys, a
returning visitor's browser could keep serving last week's *cached* `app.js` indefinitely, even after
a new version was deployed — a stale-cache bug that's invisible to the developer (their own cache is
usually fresher) and maddening to reproduce for users. Hashing the filename by content means a
changed file is a *new URL*, and an unchanged file (say, a bookmarked-forever font Vite decided not
to touch) keeps its old URL and its cache — you get "cache forever, safely" instead of "cache briefly
and hope," because the browser never has to guess whether a given URL's content might have changed.

**Why would you never want to deploy the dev server itself to real users, even though it "works"?**

The dev server transforms every file *on every request, on the fly*, un-minified, with full source
maps and an HMR WebSocket connection kept open to every client — none of that work happens once,
ahead of time; it happens per-request, forever, for as long as the process runs. That's the right
trade for a developer editing files every few seconds (instant feedback beats a precomputed bundle),
but it means every real visitor's request pays a transform-and-serve cost a production build pays
exactly once (at build time, not per-request), ships far more bytes (unminified, unbundled, with dev
tooling attached), and depends on a long-lived Node process and WebSocket connection that has no
place in a static-hosting/CDN deployment story like GitHub Pages (Demo 9).

**Real format finding:** `npx prettier --check .` flagged several files' long concatenation lines
exceeding the 100-char print width (e.g. `utils.js`'s `formatDate`, which built its return value as
one 115-character line). Fixed by hand to match Prettier's exact expected reflow (verified against a

### Questions

**What's the difference between what a linter checks/fixes and what a formatter checks/fixes? Give
one concrete finding from each tool on this codebase.**

A linter analyzes *meaning*: is this variable ever used, is this comparison always true, does this
`await` sit outside an `async` function — questions a formatter has no opinion on because they're not
about whitespace or punctuation. A formatter enforces *layout*: line length, quote style,
indentation, trailing commas — questions a linter mostly ignores because they don't change what the
code does. Concrete findings from this exact codebase: ESLint's `'resolvedTerm' is defined but never
used` is a meaning-level finding (dead code, no visual difference on screen). Prettier's line-length
reflow of `formatDate`'s return statement is a pure layout finding (identical behavior before and
after, only the line breaks moved).

**Why are `lint` and `lint:fix` two separate scripts instead of one that always auto-fixes? When
would you deliberately want the non-fixing version?**

Because not every finding is safe to auto-fix. The `resolvedTerm` unused-variable finding above is
the textbook case: ESLint *could* guess ("delete the parameter"), but that's a decision about intent
a tool shouldn't make silently — maybe the parameter was meant to be used and its absence is the
actual bug, not the presence. Running plain `lint` (no `--fix`) is what you want in CI (Demo 8): CI
should *report* problems and fail the build, never silently rewrite a contributor's just-pushed code
before anyone's reviewed the diff. `lint:fix` is a local, deliberate, "I want to accept what the tool
suggests" action a developer runs on their own machine and then reviews before committing.

**What does `npm run lint` actually do under the hood? Where does npm look for the `lint` command,
and would it work if the linter weren't installed as a project dependency?**

`npm run lint` reads the `"lint": "eslint ."` entry from `package.json`'s `scripts` block and runs
that string as a shell command — but first it prepends `node_modules/.bin` to the `PATH` for the
duration of that one command. `node_modules/.bin/eslint` is a small shim npm creates automatically
when `eslint` is installed as a (dev)dependency, pointing at the actual installed package's CLI entry
point. If ESLint were only installed *globally* on the developer's machine and not as a project
dependency, `npm run lint` would still very likely find *a* `eslint` on `PATH` and run it — but it
would be whatever version happens to be globally installed on that one machine, not the version
pinned in `package-lock.json`, defeating the entire reproducibility point of Demo 1's lockfile
discussion. Installing it as a devDependency guarantees `npm run lint` runs the *exact same* linter
version for every contributor and for CI, regardless of what (if anything) is installed globally.

## Demo 5 — TypeScript setup & first conversions

### Tasks — what was done

`tsconfig.json` — `strict: true` plus, deliberately turned on beyond the `strict` bundle:
`noUncheckedIndexedAccess`, `noImplicitReturns`, `noFallthroughCasesInSwitch`,
`forceConsistentCasingInFileNames`. `moduleResolution: "bundler"` so every import specifier keeps its
`.js` extension (`import { state } from "./state.js"`) while actually resolving to `state.ts` on
disk — this is what let every single file conversion in this exercise happen with **zero import
statement changes** anywhere in the codebase. `allowJs: true` / `checkJs: false` so the mixed
`.js`/`.ts` tree at every intermediate demo stage kept type-checking cleanly. `noEmit: true` — Vite's
own transform pipeline does the actual JS output; `tsc` here is purely a checker.

First conversions (no `any` anywhere): `utils.js` → `utils.ts`, `state.js` → `state.ts`,
`storage.js` → `storage.ts`. Wired into tooling: `build` is `tsc --noEmit && vite build`
(**verified live**: temporarily changed a parameter's type to `number` where a `string` was actually
passed — `npm run build` failed at the `tsc` step with `TS2339: Property 'toLowerCase' does not
exist on type 'number | ""'` and never reached `vite build`; reverted, `npx tsc --noEmit` back to
exit 0). `dev` runs `vite` and `tsc --noEmit --watch` together via `concurrently`, confirmed live:
`Found 0 errors. Watching for file changes.` printed alongside Vite's own ready banner.

### Questions

**What does `strict` actually turn on? Name at least two individual checks bundled under it, and say
whether you kept it on and why.**

`strict: true` is shorthand for a bundle of otherwise-separate flags, including (among others)
`strictNullChecks` (a value typed `string` can never actually be `null`/`undefined` unless the type
says so — `string | null`) and `noImplicitAny` (every value must have an inferable or explicit type;
an unannotated function parameter TypeScript can't infer becomes a hard error instead of silently
`any`). Kept on, deliberately: `strictNullChecks` alone is what turned every un-guarded
`document.getElementById(...)` call in this codebase into a real compile error to think about (see
Demo 7) — exactly the class of `Cannot read properties of null/undefined` runtime crash Exercise 1's
bug-hunt demos were built around. Turning it off would make the whole exercise close to pointless:
almost every interesting decision documented in Demo 7 exists because of `strictNullChecks`.

**What's the difference between a compile-time type error and the runtime bugs you fixed in
Exercise 1? Could TypeScript alone have caught any of those specific bugs? Why or why not?**

A compile-time type error is caught by `tsc` *before the code ever runs*, purely from the shapes
declared in the source — no test execution, no specific input needed to trigger it. A runtime bug
only manifests when the program actually executes a particular path with particular data. Checking
Exercise 1's bug list against what static types can see: the **mutation/reference bug** (Demo 2,
`state.filteredEvidence = state.allEvidence` — same array, not a copy) is *not* a type error at all —
both sides of that assignment are `Evidence[]`, so it type-checks perfectly; the bug is about object
*identity*, which TypeScript's structural type system has no way to represent or complain about. The
**async/Promise flag-never-reset bug** (Demo 3, `evidenceViewLoading` never set back to `false`) is
similarly invisible to a type checker — the flag is a valid `boolean` at every point; the bug is a
missing statement, not a wrong type. The **`var`/`let` closure bug** (Demo 4) *is* closer to
something a linter (not a type checker) can flag — `no-var`-style rules exist precisely because of
this class of bug — but it's not a *type* error either; `var i` is still a perfectly well-typed
`number`. In short: no, none of Exercise 1's specific bugs were type errors, because none of them
were about a value having the *wrong shape* — they were about control flow, aliasing, and scoping,
categories TypeScript's type system isn't designed to reason about.

**What does `any` do to TypeScript's checking for a value, and why did you avoid it in this first
pass even though it would have been faster?**

`any` doesn't just mean "unknown type" — it's a full opt-out: once a value is `any`, every property
access, every function call, every assignment to/from it skips type-checking entirely, and that
"infectiousness" spreads to anything the `any` value touches (assign an `any` to a `string`-typed
variable and that variable's later uses go unchecked too, silently). It would genuinely have been
faster to type these first three modules' trickier bits as `any` and move on. Avoided it because the
entire point of this pass is to have a small, real, `any`-free foundation (`utils.ts`'s generic
`<T extends { id: string }>` helpers, `state.ts`'s `unknown[]` placeholders) that later demos build on
without ever having to "come back and actually type this properly" — `any` in a migration has a
tendency to become permanent, since nothing forces anyone to ever revisit it.

## Demo 6 — Typing the domain data

### Tasks — what was done

`js/types.ts`: `CaseData`, `Person`, `Location`, `Evidence` (`status`/`relevance` as strict 3-value
unions), `TimelineEvent` (`certainty` deliberately left as plain `string` — see Q3).
`dataLoader.js` → `dataLoader.ts`, converted to use these types instead of raw `fetch().json()`
results (each `.json()` call now has an explicit `as CaseData`/`as Person[]`/etc.); `state.ts`'s
placeholder `unknown[]` fields from Demo 5 refined to the concrete domain types now that they exist.

### Questions

**Walk through the ambiguous field you picked: how did the JavaScript version get away without
deciding on one shape, and what did TypeScript force you to commit to?**

Picked `personIds` (on both `Evidence` and `TimelineEvent`). `utils.js`'s `evidenceMentionsPerson`
has always done `ev.personIds.indexOf(person.id) !== -1 || ev.personIds.indexOf(person.name) !== -1`
— checking the array against *both* a person's `id` slug (`"kernel-colt"`) and their display `name`
(`"Kernel Colt"`). An untyped JS array can hold a mix of both shapes forever without anyone having to
say so out loud; nothing about `[]` (or `Array`) requires its elements to agree on what they
represent. Modeling this field in TypeScript forces a decision, because `Evidence.personIds` needs
*some* declared element type. The honest options were: (a) pretend it's cleanly `id: string` and let
the type lie about the actual data, or (b) name the ambiguity. Went with (b) —
`type PersonRef = string; // a Person's \`id\` OR (inconsistently) their \`name\`` — because option
(a) would have been strictly *less* accurate than the untyped version: at least untyped JS never
claimed anything about the shape.

**Is there a data-shape problem here TypeScript's static types can't catch on their own, because bad
data would only show up at runtime from a JSON file? What would you need in addition to types?**

Yes, and it's the closely-related field: `evidence.json` entry `E12` stores `status`/`relevance` as
`"Reviewed"`/`"Unknown"` (capitalized) while every other entry uses lowercase. `Evidence.status` is
typed as the strict union `"unreviewed" | "reviewed" | "flagged"`, and `dataLoader.ts` does
`const data = (await res.json()) as RawEvidence[]` — but `as` is a **type assertion**, not a runtime
check: it tells the compiler "trust me, this is shaped like `RawEvidence[]`" and the compiler does
exactly that, unconditionally, whether or not the actual JSON agrees. If `E12`'s `"Reviewed"` had been
left un-normalized, TypeScript would have been completely happy to let it flow through as a
`EvidenceStatus`-typed value that, at runtime, doesn't equal any of the three literals the type
claims it can be — a silent lie the type system can't detect because `JSON.parse`'s return type is
`any`, and casting `any` to anything is always accepted. What you'd need *in addition* to static
types to actually catch this: a runtime validation/schema library (e.g. Zod, or a hand-written type
guard function that inspects the parsed value's actual fields before trusting it) that runs *after*
`JSON.parse` and *before* the `as` cast, so a malformed value fails loudly at load time instead of
silently misbehaving three files away, later, when something finally reads it. This project's actual
fix (`normalizeStatus`/`normalizeRelevance` in `dataLoader.ts`) is a narrow, hand-written version of
exactly that idea, scoped to the one field that needed it, rather than a general-purpose schema
validator.

**What's the difference between an `interface` and a `type` alias for an object shape? Which did you
use, and does it actually matter here?**

Both can describe an object's shape and are used almost interchangeably for that in modern
TypeScript; the practical differences are narrower than they're often made out to be: `interface`
supports declaration merging (two `interface Foo {}` declarations in scope combine into one) and is
generally what the TypeScript team recommends by default for object shapes; `type` is required for
anything that isn't a plain object shape — unions (`EvidenceStatus`), mapped/conditional types, or a
type built from `Omit<...> & {...}` the way `dataLoader.ts`'s `RawEvidence` is. This project uses
`interface` for the domain models (`Person`, `Location`, `Evidence`, `TimelineEvent`, `CaseData`,
`AppState`) — the recommended default for "this is an object with these fields" — and `type` for
everything that's fundamentally a union or a derived/computed shape (`EvidenceStatus`,
`EvidenceRelevance`, `PersonRef`, `RawEvidence`). It doesn't meaningfully matter for this app's size:
nothing here relies on declaration merging, and every shape used is simple enough that either keyword
would compile to the same checking. The choice here is about following the shape-vs-union convention
consistently, not about a real behavioral difference this project depends on.

## Demo 7 — Full migration & resolving type errors across the app

### Tasks — what was done

Prettier code style!"; `npm run build` (the `tsc` gate, then `vite build`) succeeds, producing a

— which correctly still resolves to the matching `.ts` source — `data/case.json`, and

### Questions

**Show one specific type error you had to actually think about. What did it tell you that plain JS
review or testing hadn't?**

`timeline.ts`'s `openEvidenceModal`: `let modal = document.getElementById("quickViewModal");` is
reassigned inside `if (!modal) { modal = document.createElement("div"); ... }`, and TypeScript
correctly narrows `modal` to non-null immediately after that block — but the very next thing the
original code did was reference `modal` again *inside* a `modal.addEventListener("click", (e) => {
... })` callback, and TypeScript refused to carry the non-null narrowing into that closure body
(`modal` is possibly `null` again there, per the compiler). This wasn't wrong of the compiler to
flag, and it wasn't something plain JS review had ever caught, because the code genuinely *was* safe
— just not in a way a type-checker (or, honestly, a careful human skim) can verify by local
inspection alone: it's safe only because nothing between the narrowing point and the closure's
*creation* reassigns `modal` again, a fact that's true today but is exactly the kind of invariant that
silently breaks the next time someone edits this function and doesn't realize a reassignment they add
in between invalidates it. The fix (`const modalEl = modal;` right after the narrowing, and using
`modalEl` inside the closure) doesn't just satisfy the compiler — it makes the invariant permanent and
checkable, instead of "true right now if you trace the whole function by hand."

**When (if ever) is reaching for `any` the right call during a migration, versus a sign you should
model the type properly? Where did you draw that line?**

`any` earns its keep when the *actual* type is either genuinely unknowable at that point in the code
(rare) or when modeling it precisely would cost real effort for a spot that has no real risk attached
— and even then, `unknown` (which still forces a narrowing check before use) is almost always the
better choice over `any` (which forces nothing). This migration reached for a type *assertion*
(`as EvidenceStatus`, `as RawEvidence[]`) several times instead — a deliberate, narrower tool than
`any`: an assertion silences the checker for exactly one expression, at exactly one point, rather than
poisoning every future use of a value the way `any` does. The line drawn: an `as` cast is fine when
there's a *specific, local, verifiable reason* the runtime value can only be what's claimed (e.g.
`evidence.ts`'s `(e.target as HTMLSelectElement).value as EvidenceStatus` — safe only because that
exact `<select>`'s options were generated, two lines earlier in the same file, from those same three
literal string values, so no other string can reach that line). It would **not** be fine to reach for
that same cast on a value that ultimately traces back to arbitrary user input or an external API
response with no such local guarantee — that's exactly the `E12` casing situation from Demo 6, and
the actual fix there was a real runtime normalizer, not a wider cast.

**Did the migration reveal a genuine, previously-unnoticed bug (as opposed to just noise)? If yes,
explain it.**

Yes — the `E12` `status`/`relevance` casing issue (Demo 6). Before this migration, that evidence
item's badge rendered with different capitalization ("Reviewed" instead of "reviewed") than every
other card on the Evidence page — a real, live visual inconsistency, just an easy one to miss in a
quick scan since the layout and colors were otherwise identical. It only became impossible to ignore
*because* `Evidence.status` had to be given a real, closed type to satisfy the compiler: the moment
there's a concrete "this field can only be one of these three exact strings" claim in the code, the
raw JSON's `"Reviewed"` stops quietly slipping through and has to be actively reconciled with that
claim (via the `normalizeStatus` function `dataLoader.ts` now applies at load time). The other
compiler-flagged spots documented above (`Date` subtraction, the closure-narrowing case, the hash
validation in `router.ts`) are judged **not** genuine bugs — in each of those, the original JS
behavior was already correct; TypeScript was refusing a pattern that happened to be safe *this time*,
not one that was actually broken.

## Demo 8 — GitHub Actions: development workflow

### Tasks — what was done

`.github/workflows/ci.yml`: triggers on `push` (every branch) and `pull_request`. One job
(`lint-format-typecheck`) with steps: checkout (`actions/checkout@v4`), Node setup

watching a second run go green. Locally verified the equivalent both ways instead: introduced a real

confirmed both pass cleanly (`exit=0`) once fixed — the same commands this workflow runs, just not
yet inside an actual Actions run. The live push→fail→fix→pass cycle still needs to happen before
class.

### Questions

**What is the difference between a workflow, a job, and a step? Point to one of each in your workflow
file.**

A **workflow** is the whole YAML file and everything it describes — `ci.yml` in its entirety. A
**job** is one unit of work that runs on its own fresh runner VM; `ci.yml` has exactly one,
`lint-format-typecheck`. A **step** is one command or action *within* a job, run sequentially on that
same runner/filesystem; `- name: Lint / run: npm run lint` is one step among the six inside that job.
Jobs in the same workflow can run in parallel and don't share filesystem state unless you explicitly
pass artifacts between them (relevant in `deploy.yml`, Demo 9, where the `build` job's output has to
be explicitly uploaded as an artifact for the `deploy` job to consume); steps within one job always
run in order, on the same checkout, and can freely depend on files/state earlier steps left behind.

**Why should lint/format run in CI at all, if it already runs (or could run) on every developer's own
machine before they push?**

Because "could run locally" and "did run locally, on this exact commit, by everyone" are very
different guarantees. Nothing stops a contributor from skipping `npm run lint` locally, having a
stale `node_modules` with an older linter version, or simply forgetting — and none of that is
enforced or even visible until CI either agrees or disagrees. CI is the one place every commit that's
about to be merged is checked the *same* way, with the *same* pinned tool versions
(`package-lock.json`, Demo 1), regardless of what any individual contributor's machine happened to
have installed or remembered to run. It's the difference between a convention and a gate.

**What is dependency caching doing here, and what would happen (correctness- and speed-wise) if you
removed it?**

`actions/setup-node@v4`'s `cache: npm` option hashes `package-lock.json` and uses that hash as a
cache key for `~/.npm`'s download cache; on a cache hit, `npm ci` restores previously-downloaded
package tarballs from GitHub's Actions cache instead of re-fetching every one of them from the npm
registry over the network. Removing it: **speed** — every run re-downloads the full dependency tree
from scratch, which is slower and adds load on the registry for no reason, since the lockfile (and
therefore the exact set of packages needed) usually hasn't changed between runs. **Correctness** —
mostly unaffected day-to-day (the cache is keyed to the lockfile hash, so a changed lockfile
correctly misses the cache and re-resolves), but removing it *doesn't* change what gets installed —
it only makes every run pay the network-download cost that a cache hit would otherwise skip, and adds
a very small extra exposure window to registry flakiness (a failed download failing an otherwise-fine
commit's CI run).

## Demo 9 — GitHub Actions: deployment workflow

### Tasks — what was done

`.github/workflows/deploy.yml`: triggers on `push` to `main` plus `workflow_dispatch` (manual
re-run). Two jobs: `build` (checkout → setup-node → `npm ci` → `npm run lint` → `npm run build` →
`actions/upload-pages-artifact@v3` on `dist/`) and `deploy` (`needs: build`;
`actions/deploy-pages@v4`). `permissions:` scoped to exactly `contents: read`, `pages: write`,
`id-token: write` — no repository secrets configured or needed at all.

**Not completed in this session, by explicit instruction not to touch git, and requiring a one-time
manual step besides:** before this workflow can publish anything, the repository's
**Settings → Pages → Build and deployment → Source** must be set to **"GitHub Actions"** (not
"Deploy from a branch") by hand in the GitHub web UI — no workflow file can set this. After that, an
actual push to `main` is needed to trigger the workflow, get a real deployed URL, and confirm the
live site serves the app end-to-end (not just that the workflow reports success) — the task's own
distinction, and one that genuinely can't be verified from workflow YAML alone.

### Questions

**Why does the deploy workflow re-run lint and build itself, instead of trusting "it already passed
on my machine" or reusing `ci.yml`'s result?**

Two independent reasons. First, workflows triggered by different events (`ci.yml` on every push,
`deploy.yml` only on push-to-`main`) run as genuinely separate Actions runs with no shared filesystem
or build artifacts by default — there's no "result" of `ci.yml` sitting anywhere `deploy.yml` could
cheaply reuse without deliberately wiring up cross-workflow artifact passing, which adds real
complexity for a benefit that mostly doesn't exist here (rebuilding is fast: fewer than 20 files).
Second, and more fundamentally: "it already passed on my machine" was never actually true from CI's
perspective — the only thing that ever ran the checks was *this specific commit*, and the only
trustworthy confirmation that *this exact commit, about to be published,* still builds and lints
clean is running those checks again, right now, in the same job that's about to publish it. Trusting
an earlier result (from a human's machine, or even from a different workflow run against a
theoretically-identical commit) reintroduces exactly the "works on my machine" gap Demo 1's lockfile
discussion and Demo 8's CI discussion both exist to close.

**What is the actual mechanism your deploy workflow uses to publish to GitHub Pages? Explain,
concretely, what it does.**

Two purpose-built, first-party GitHub Actions, not a `git push` to a `gh-pages` branch. The `build`
job's last step, `actions/upload-pages-artifact@v3`, packages the `dist/` folder into a tarball and
uploads it as a special "Pages artifact" associated with this workflow run (visible in the run's
Artifacts list, but typed specifically for Pages rather than a generic build artifact). The `deploy`
job then runs `actions/deploy-pages@v4`, which: requests a short-lived OIDC token (enabled by this
workflow's `id-token: write` permission) proving "this run belongs to this specific repository and
workflow"; presents that token to GitHub's Pages deployment API along with a reference to the
uploaded artifact; and GitHub's own infrastructure takes it from there, publishing that exact artifact
to the project's Pages URL. At no point does this workflow's own runner push a commit, create a
branch, or otherwise touch the repository's git history — publishing happens entirely through the
Pages API, authenticated by the OIDC token rather than a stored credential.

**What would you need to change if you were deploying to a different static host instead (e.g.
Netlify, Vercel, a plain server over SFTP)? What would stay the same?**

**Stays the same:** the entire `build` job — checkout, Node setup, `npm ci`, `npm run lint`,
`npm run build` — is completely host-agnostic; it just produces a `dist/` folder, and every static
host wants exactly that. **Changes:** everything after the build. `permissions:` would drop
`pages`/`id-token` entirely (those are GitHub-Pages-specific) and instead the workflow would need
*some* credential for the target host, stored as an encrypted **GitHub Actions secret**
(`secrets.NETLIFY_AUTH_TOKEN`, `secrets.VERCEL_TOKEN`, or an SSH private key for SFTP) rather than
relying on GitHub's own OIDC trust relationship — a real, meaningful downgrade in the credential story
(a leaked long-lived token is a bigger blast radius than a short-lived OIDC token scoped to exactly
this repo and workflow). The publish step itself would swap `actions/deploy-pages@v4` for that host's
own official action (`netlify/actions/cli`, `amondnet/vercel-action`, or a generic
`appleboy/scp-action`/`rsync` step for SFTP) pointed at `dist/`. The `upload-pages-artifact` step
would simply be dropped — those other hosts' actions read straight from the `dist/` folder on the
same runner instead of going through GitHub's own artifact-then-publish handoff.

## Demo 10 — Workflow triggers, permissions & failure modes

### Tasks — what was done

**Not completed in this session, by explicit instruction not to touch git:** deliberately committing
a real TypeScript error or lint failure, pushing it, and watching `deploy.yml` fail before reaching
the `deploy` job; reading a real failed run's logs live in the Actions tab. Both were instead verified
**locally**, against the exact commands the workflow runs: earlier in this exercise (Demo 5), a
parameter was temporarily mistyped as `number` where a `string` was actually used, and `npm run
build` (`tsc --noEmit && vite build`) failed at the `tsc` step with a real, readable `TS2339` error,
never reaching the `vite build` half of the same script — which is exactly the failure mode
`deploy.yml`'s `build` job would hit before its `deploy` job (gated by `needs: build`) could ever
start. The genuinely live parts — an actual failed Actions run's logs, and reading them for someone
unfamiliar with the repo — still need to happen before class.

### Questions

**When your build step fails, does the previously-deployed version stay live, get taken down, or
something else? Is that the behavior you want?**

Stays live, untouched. `deploy.yml`'s `deploy` job is declared with `needs: build`, so a failed
`build` job means the `deploy` job never starts at all — `actions/deploy-pages@v4` is simply never
invoked, and GitHub Pages only ever updates what's published when that action successfully completes.
There is no "half-deployed" or "broken" published state this workflow can produce; the site just
keeps serving whatever the *last successful* deploy published, indefinitely, until a future push both
builds cleanly and reaches the `deploy` job. This is exactly the behavior wanted: a broken commit
should never be able to take down a working, already-live site — the failure is visible (a red run in
the Actions tab) without being destructive.

**What GitHub Actions permission(s)/secret(s) does your deploy workflow actually need, and where are
they configured? What's the security risk of over-granting?**

Exactly three permissions, declared in `deploy.yml`'s top-level `permissions:` block: `contents:
read` (checkout needs to read the repo; nothing in this workflow ever writes to it), `pages: write`
(lets the workflow publish to this repo's Pages site), and `id-token: write` (lets the `deploy` job
mint the short-lived OIDC token `actions/deploy-pages@v4` needs). **No repository secrets are
configured or required at all** — this is deliberate; the OIDC-based Pages deployment flow exists
specifically so a workflow doesn't need a stored long-lived credential (a personal access token, an
SSH key) that could leak from logs, a compromised dependency, or a malicious PR that manages to print
`secrets.*` somehow. The security risk of over-granting here concretely: had this workflow requested
`contents: write` instead of `read` (easy to reach for reflexively, since "write" sounds like the safe
default for "a workflow that publishes something"), any code able to run inside this workflow — a
malicious dependency executed during `npm ci`, say — could push arbitrary commits to the repository
itself, not just publish a Pages build. Scoping to the minimum each job actually does is what limits
the blast radius of exactly that kind of compromise.

**What's the difference between `on: push`, `on: pull_request`, and `on: workflow_dispatch`? Which
did you use for Demo 8 vs. Demo 9, and why is that pairing correct?**

`on: push` fires whenever commits land on a matching branch/ref — the workflow runs against the code
*as it now exists* on that branch. `on: pull_request` fires when a PR is opened/updated, and
critically runs against the **merge** of the PR's changes into its target branch (not just the PR
branch alone) — it's specifically about validating "if this were merged, would it still be green,"
which is a different question than "did this branch's tip pass." `on: workflow_dispatch` is a purely
manual trigger — a human (or another workflow) clicks a button or calls the API to run it on demand,
with no code change required at all. Used `push` + `pull_request` (unrestricted) for `ci.yml`
(Demo 8) — the cheap, constant feedback loop belongs on every branch and every proposed merge, since
its whole job is to catch problems as early and as often as possible. Used `push` scoped to
`branches: [main]` plus `workflow_dispatch` for `deploy.yml` (Demo 9) — a real deployment should only
ever be triggered by code actually landing on the branch that represents "live," not by every
feature-branch push or every open PR (which hasn't been merged and may never be); `workflow_dispatch`
is kept alongside it purely as a manual escape hatch to re-publish on demand (e.g. after a Pages
outage) without needing a throwaway commit. That pairing — broad-and-constant for validation,
narrow-and-deliberate for publishing — is the right split precisely because "check code" and "publish
code" are different-risk operations that deserve different trigger philosophies.
